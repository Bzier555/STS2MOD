# Enchanted Rewards

An STS2 Custom Run modifier. Normal fights offer an enchantment for a card already in your deck
instead of a new card. Elite fights keep their card reward but no longer grant a relic. Boss fights
are unchanged.

See `../EnchantedRewards_STS2_Mod_Spec.md` for the full design. The full enchantment pool
(`EnchantmentPool.Factories`) is offered now - every non-deprecated enchantment except
`SlumberingEssence` (reported non-functional). A card can carry any number of enchantments, of any
mix of types: the first ever applied goes into the card's native slot (for maximum compatibility
with everything that reads it - see `EnchantmentService`), and *every* application after that
(whether the same type again or a different one) becomes an independent "extra" (see
`ExtraEnchantments`) - never merged into an existing instance's `Amount`, so "does stacking this
actually do more" simply falls out of each instance independently contributing through the normal
hook dispatch (two Instinct copies each independently contribute their own 2x multiplier, compounding
to 4x; two Spiral copies each independently add their own +1 replay). `EnchantmentPool.
BenefitsFromRepeatApplication` is what decides whether repeating a given type is even offered again
in the first place (no point offering, say, a second `RoyallyApproved` - keywords are idempotent).

**Known limitation**: extra (non-slot-1) enchantments are tracked in memory only for now (a plain
`ConditionalWeakTable`, not one of BaseLib's save-integrated fields) - they work correctly for the
rest of the current play session, but are lost on save/quit and reload (only whatever's in the
card's native slot survives that). See `ExtraEnchantments`'s doc comment and spec Part 1.4 for why
this was deliberately deferred rather than risked half-verified.

Clicking the reward now offers a choice between (up to) two different enchantments - only ones
with at least one valid target in the current deck are ever offered (e.g. Nimble never shows up if
nothing in the deck currently gains block) - via `MegaCrit.Sts2.Core.Rewards.LinkedRewardSet`, then
the card-picker screen for whichever one was chosen.

## Build

Requirements:

- Slay the Spire 2 0.107.1 or newer
- .NET SDK 9
- BaseLib 3.4.5 or newer installed in the game's `mods/BaseLib` directory

Run:

```powershell
dotnet build EnchantedRewards.csproj -c Release
```

The compiled assembly is written to `bin/Release/net9.0/`. To install the mod, place
`EnchantedRewards.dll` and `EnchantedRewards.json` in a `mods/EnchantedRewards` directory under the
game installation.

## Implementation notes

- Registration uses BaseLib's `CustomModifierModel`; localization is injected in code (`ILocalizationProvider`), so no PCK is required.
- Reward replacement overrides `AbstractModel.TryModifyRewards`, the same extensibility point relics like Prayer Wheel use - no Harmony patch needed for this part.
- The enchantment is rolled and its valid target cards resolved *before* the reward is even shown (mirrors `SpecialCardReward`), so the player is never offered a reward they can't take; if nothing in the deck qualifies, a gold reward is substituted instead.
- Card selection reuses the game's own (currently unused-by-content) `NDeckEnchantSelectScreen`/`CardSelectorPrefs.EnchantSelectionPrompt` picker - no custom UI was built.
- Multiplayer selection sync reuses `PlayerChoiceSynchronizer` + `PlayerChoiceResult.FromMutableDeckCard`, the same mechanism the base game uses to reference a specific persistent-deck card across clients.
- The enchantment pool (`EnchantmentPool`) is a hand-maintained list, not a reflection scan, and currently excludes every enchantment whose effect relies on `OnPlay` (`Swift`, `Sown`, `Adroit`, `Corrupted`, `Momentum`, `Inky`) - those need the `CardModel.OnPlayWrapper` patch from spec Phase 5 before they'd work correctly once the multi-enchant layer exists.
- Same-type stacking (`EnchantmentService.Apply`) deliberately bypasses `EnchantmentModel.CanEnchant`'s native same-type check, because that check requires the enchantment to opt in with `IsStackable => true` and none of the shipped enchantments currently do. `EnchantmentPool.StacksMeaningfully` limits this to the enchantments whose effect actually reads `Amount` (`Sharp`, `Nimble`, `Vigorous`, `Goopy`) so a reward is never offered that would have zero effect.
- **Bugfix**: `EnchantmentPool`'s factories now return the *canonical* enchantment instance (no `.ToMutable()`). `NDeckEnchantSelectScreen` calls `.ToMutable()` on whatever it's handed internally for its own preview, and `EnchantmentModel.ToMutable()` asserts the instance is canonical first - handing it an already-mutated instance made that assertion throw, which aborted `_Ready()` partway through (before it set the enchantment icon/title/description text, leaving the scene's placeholder art/text in place) and later left the card-selection preview panel's Confirm button never enabled (an apparent hang). `EnchantmentService.Apply` now makes its own mutable clone right before actually attaching an enchantment to a card.
- **Bugfix**: enchantment amounts now come from `EnchantmentPool.DefaultAmountFor`, matching what real relics/events grant (`Sharp` 3, `Nimble` 2, `Vigorous` 8 - found by searching the decompiled assembly for every `CardCmd.Enchant<T>` call site) instead of a flat `1` for everything.
- **Multi-enchant ("extra slot") layer**: `ExtraEnchantments` tracks enchantments beyond a card's native slot, keyed by `CardModel` reference. Combat-time effect comes from two places: `ModHelper.SubscribeForCombatStateHooks` (registered in `EnchantedRewardsMod`) makes extras participate in the game's *generic* `AbstractModel` hook dispatch (`AfterCardPlayed`, `ModifyShuffleOrder`, `AfterCardDrawn`, `BeforeFlush`, `AfterAutoPrePlayPhaseEntered`) automatically, since those enchantment classes already implement those methods correctly; `EnchantedRewardsModifier`'s overrides of `ModifyDamageAdditive`/`ModifyDamageMultiplicative`/`ModifyBlockAdditive`/`ModifyBlockMultiplicative`/`ModifyCardPlayCount` handle the combat-*math* hooks, which the base game only ever asks a card's single native `Enchantment` for. Validity checking for a genuinely different enchantment type on an already-enchanted card can't reuse `EnchantmentModel.CanEnchant` directly (it always refuses whenever the card has *any* enchantment) and can't use `CardModel.CreateClone()` to get a scratch copy to test against either (it throws outside of combat, which is exactly when reward selection happens) - so `EnchantmentPool.MeetsRestrictionsIgnoringExistingEnchantment` re-implements each pool enchantment's *other* restrictions directly instead (verified against the decompiled source; keep it in sync if the pool ever changes).
- **Decompiler/game-version gotcha hit during this work**: `AbstractModel.ModifyDamageAdditive`/`ModifyDamageMultiplicative`'s real parameter list has changed *twice* across this project - once because the `ilspycmd` version used here (8.2.0) silently dropped a trailing `CardPlay cardPlay` parameter in C#-source-mode decompile (only visible via `-il`), and then again because Slay the Spire 2 is actively patched and a later game update genuinely removed that parameter from these two methods (confirmed with a throwaway console app doing `typeof(AbstractModel).GetMethod(...).GetParameters()` via reflection against the live `sts2.dll` - much faster and more reliable than decompiling for a quick signature check, worth reaching for first next time an override mysteriously won't compile). If this ever happens again, re-verify with reflection before assuming the code is at fault.
- **Elite relics removed**: `TryModifyRewards` now also handles `RoomType.Elite`, stripping any `RelicReward` from the rewards list (the `CardReward` stays - only the bonus relic is cut).
- **Bugfix**: after picking one of the two linked enchant options, the reward screen wasn't recognizing the choice as resolved (both options stayed interactive-looking and "Skip" never became "Proceed"). Root cause, found by reading `MegaCrit.Sts2.Core.Rewards.Reward.SelectUnsynchronized()` and `RewardsSetSynchronizer`: when a `LinkedRewardSet` child succeeds, the base game calls `ParentRewardSet.OnSelect()` directly rather than through `SelectUnsynchronized()`, so the `LinkedRewardSet` itself never gets `SuccessfullySelected` set to `true` - and `RewardsSet.AllRewardsSuccessfullySelected` (which both the "Skip"/"Proceed" text swap and the backend's reward-set-completion tracking depend on) checks exactly that flag on the *top-level* reward (the `LinkedRewardSet`), not its children. This looks like a genuine bug in `LinkedRewardSet` itself - it has no other (native or modded) callers anywhere in the decompiled assembly to have exposed it before. `EnchantReward.OnSelect()` now fixes up `ParentRewardSet.SuccessfullySelected` via reflection (its setter is private) once one of the two options is chosen, since there's no public API for it. **Not fixed**: `RewardsSetSynchronizer.SelectLocalReward` also computes `set.Rewards.IndexOf(reward)` for its network message, which likewise can't find a nested `LinkedRewardSet` child and sends an invalid index - this only matters for multiplayer (remote peers would fail to resolve the message) and would need a netcode-level patch; out of scope until multiplayer testing actually surfaces it.
- **Critical bugfix ("all Defends gain 100 block")**: `EnchantedRewardsModifier`'s four combat-math overrides (`ModifyDamageAdditive`/`Multiplicative`, `ModifyBlockAdditive`/`Multiplicative`) were returning a *running total* (original amount plus/times our contribution) instead of *just our own contribution*. `AbstractModel`'s own defaults return `0m`/`1m` (confirmed against real listeners like `StrengthPower.ModifyDamageAdditive`, which returns only `base.Amount`, and `VulnerablePower.ModifyDamageMultiplicative`, which returns only `1.5m`) - the caller is what sums/multiplies every listener's contribution into the real total. Since this modifier is a hook listener for *every* card play, not just ones with extra enchantments, the old code caused the caller to add our already-inflated return value on top of the real total again and again on every recomputation (e.g. live UI hover preview), snowballing into huge numbers. Fixed to always return the identity value (`0m`/`1m`) plus/times only what the card's *extra* enchantments contribute.
- **Removed `SlumberingEssence` from the pool**: reported as not actually doing anything in practice. Its effect is dispatched through the same generic hook path as its still-working siblings (`PerfectFit`, `Slither`), so the precise root cause isn't confirmed - excluded rather than left offering a reward with no effect (see `EnchantmentPool`'s comment).
- **Extra-enchantment "flags" on cards**: `CardEnchantmentVisualsPatch` postfixes `NCard.UpdateEnchantmentVisuals` to clone the native single enchantment "flag" (icon + amount number) once per extra enchantment via Godot's `Duplicate()`, so a multi-enchanted card actually shows all of its enchantments instead of just the native slot's. This is the one change in this round that couldn't be verified by reading decompiled source alone (it's real-game visual behavior); known gaps: no hover tooltip on the duplicated flags yet, no "disabled this turn" shader treatment, and no overflow handling if a card has enough enchantments to stack off the card's edge. **Reported still only showing one flag outside the deck menu** - `UpdateEnchantmentVisuals` is the only place `NCard` touches its enchantment tab fields at all (confirmed by searching the whole decompiled `NCard.cs`), so the patch should fire identically everywhere a card is rendered; still investigating why the visual result apparently differs by screen (leading theories: the duplicated tabs' fixed pixel offset landing outside a smaller/clipped card representation elsewhere, or node-pool reuse timing - needs the specific other screen(s) it was checked in to narrow down further).
- **Bugfix attempt (partial/superseded, see next entry)**: `CardModel.UpdateDynamicVarPreview` only asks `DamageVar`/`BlockVar.UpdateCardPreview` to run the full hook chain (`Hook.ModifyDamage`/`ModifyBlock`) when the card has an active `CombatState` *and* is in the Hand or Play pile; everywhere else it only applies `card.Enchantment` (slot-1) directly. `OutOfCombatPreviewPatch` covers that gap for out-of-combat views (deck menu, etc.) and is still needed/correct - but this entry originally (and wrongly) claimed actual in-combat damage/block was unaffected. It wasn't: see below for the real, shared root cause that was *also* breaking in-combat behavior.
- **Root-cause bugfix: extra enchantments invisible/inactive everywhere except the deck menu (flags *and* actual combat damage/block)**: `Player.PopulateCombatState` clones every persistent deck card into a **new `CardModel` instance** for the draw pile (`state.CloneCard(item)`) at the start of every combat - the card that ends up in your hand, gets played, and deals damage is never the same object as the one sitting in `player.Deck.Cards`. `ExtraEnchantments` is a `ConditionalWeakTable<CardModel, ...>` keyed by object reference, so every lookup against a combat-instance card (`ExtraEnchantments.Get(cardSource)` in `EnchantedRewardsModifier`'s combat-math overrides, `CardEnchantmentVisualsPatch`'s flags, `AllListenersIn`'s generic-hook registration) silently found nothing - explaining *both* symptoms at once (only the deck menu, which shows persistent instances directly, ever saw extras at all) and why actual played-card damage was wrong, not just its printed preview. Fixed by having `ExtraEnchantments.Get` fall back to `CardModel.DeckVersion` - the combat clone's own link back to its persistent original, the same field native enchantments like `Goopy` already use to write changes back to the deck copy - walking the whole chain in case of a clone-of-a-clone (e.g. an in-combat duplication effect). This is the fix that should actually make multi-enchant cards work correctly in real combat, not just look right in the deck menu.

### Round 5 (playtesting after a full run)

- **Restrictions relaxed per explicit request**: `EnchantmentPool.MeetsRestrictions` (renamed from `MeetsRestrictionsIgnoringExistingEnchantment`, and now the *only* validity check - see next bullet) drops Spiral's native "must be Basic-rarity Strike/Defend" and RoyallyApproved's native "must be Attack or Skill" restrictions entirely (both were arbitrary category gates unrelated to whether the effect does anything - Innate+Retain and extra replays are meaningful on any card). Goopy's native "must have the Defend tag" was replaced with a functional `card.GainsBlock` check (matching Nimble) instead of removed outright, since a card can grant block without being tagged Defend, but the enchantment still needs *something* to add block to. Kept as-is (deliberately, not blanket-removed): Sharp/Instinct/Vigorous's Attack-only gate (their bonus only applies to a "powered attack"), Nimble/Goopy's `GainsBlock` requirement, Slither's `!CostsX`, SoulsPower's Exhaust-keyword requirement, and Imbued's native Skill-only restriction (kept out of caution - auto-playing an Attack automatically raises a targeting question nothing in Imbued's own code appears to resolve; flagged as the one judgment call in this batch, revisit if it turns out to be overly conservative).
- **Validity checking unified**: `EnchantmentPool.CanTarget` no longer calls the real `EnchantmentModel.CanEnchant` at all, not even for a card's first enchantment. It used to (only falling back to the custom, more permissive check for a card's second-or-later, different-type enchantment), which meant the relaxed rules above only applied starting from a card's *second* enchantment - a card being enchanted for the first time still hit Spiral's/RoyallyApproved's/Goopy's native restrictions. `EnchantmentService.Apply`'s slot-1 case was changed to match: it no longer calls `CardCmd.Enchant` (which would re-validate with the real, restrictive `CanEnchant` and throw for anything the relaxed rules now allow that the native check wouldn't), and instead inlines the same `card.EnchantInternal(...)` + `ModifyCard()` + history-tracking steps `CardCmd.Enchant` itself would have done, minus that gate.
- **Bugfix: Goopy (and, found during the same audit, Vigorous's disable-after-use, PerfectFit's shuffle reorder, and Slither's cost randomization) never actually doing anything as an *extra*, only as slot-1**: all four enchantments' own logic compares the specific `CardModel` instance they're attached to against the card an event is actually happening to (e.g. Goopy's `AfterCardPlayed`: `if (cardPlay.Card != base.Card) return;`). `EnchantmentModel.Card` is set once, at `EnchantmentService.Apply` time, to the *persistent* deck card - but by the time any of these hooks fire, the card actually being played is the *combat* clone (see the entry above), so the comparison was always false. The native game avoids this for slot-1 because cloning a card for combat *also* clones its `Enchantment` via `ClonePreservingMutability()` and re-points the clone's `Card` at the new combat card (`CardModel.DeepCloneFields()`) - extras never got the same treatment, since they live in a side table the native cloning code doesn't know about. Fixed with `CombatCloneSyncPatch`: postfixes `Player.PopulateCombatState` to clone each extra onto its card's combat instance (properly `Card`-linked, mirroring the native slot-1 clone), and prefixes `Player.AfterCombatEnd` to sync state (`Amount`, `Status`) back to the persistent original before combat state is torn down, so progress (e.g. Goopy's growing bonus) carries into the next fight.
- **Bugfix: an extra Spiral's replay bonus not showing in a card's "Replay N" hover tip/description text**: `CardModel.GetEnchantedReplayCount()` only ever reads the card's native slot-1 `Enchantment` directly and is used two ways - real gameplay (its result feeds `Hook.ModifyCardPlayCount`, which *does* correctly reach extras via a hook chain) and display-only (the "Replay N" hover tip and description text call it directly, no hook dispatch at all). `ReplayCountPatch` postfixes `GetEnchantedReplayCount()` itself to add extras' contribution, fixing both the hover tip and gameplay would double-count if left as separate paths - so `EnchantedRewardsModifier`'s old `ModifyCardPlayCount` override was removed; all of extras' play-count contribution now flows through this one patched method instead.
- **Bugfix: reward hover tooltip only showed the enchantment's bare name**: `EnchantReward` now overrides `ExtraHoverTips` with `EnchantmentModel.HoverTips` (the same content the card face itself would show once enchanted - title, full description, icon, plus anything the enchantment adds itself like a keyword explanation) instead of leaving it as the default empty tooltip. Needed its own throwaway mutable preview clone with `Amount` actually set first (`_enchantment` is the shared canonical pool instance, whose `Amount` is never set - reading its description directly would show "0"), mirroring exactly what `NDeckEnchantSelectScreen._Ready()` already does for its own single-card preview.
- **Known, deliberately out-of-scope limitation: native enchant-granting relics/events don't know extras exist**: things like `FresnelLens`, `WingCharm`, `GnarledHammer`, and various events all call the real, restrictive `EnchantmentModel.CanEnchant` to decide which of *your* cards they can enchant - since that check only ever looks at a card's native slot, a card with something in slot 1 (from us or natively) will correctly, safely be excluded from their candidate list, same as any other already-enchanted card. This is expected and shouldn't cause a crash or data loss. What's *not* confirmed: the user's report of a card seemingly losing a Nimble enchantment after an event granted it the `Clone` enchantment (used by a rest-site "duplicate this card" option) - plausible explanation is that the native card-duplication code that a `Clone`-enchanted card eventually triggers only clones the card's native slot-1 state (matching the same "cloning code doesn't know about extras" class of bug just fixed for combat above), producing duplicate(s) missing whatever extras the original had. Not fixed pending a clearer reproduction - patching arbitrary native relic/event card-duplication code blind, without confirming which one is actually involved, isn't a chance worth taking.

### Round 6 (playtesting: stacking still broken, "am I seeing a subset of enchantments")

- **Stacking model rebuilt (Instinct/Nimble/Adroit/Spiral, etc. weren't actually stacking)**: the previous design tried to make a repeat application of the same type increment a shared instance's `Amount`. That's wrong for most enchantments - Instinct's damage multiplier and Spiral's replay bonus are both *fixed constants* that never read `Amount` at all, so "incrementing Amount" was a complete no-op for them, and the "already has this type, only offer again if it scales with Amount" gate was blocking Instinct/Nimble entirely on cards that already had them (the user's literal report: reopening the enchant screen with Instinct already applied hid Instinct from the target list). Rebuilt so every application beyond the first is always a brand new, independent instance (`EnchantmentService.Apply`, no more merge branch) - two Instinct copies each independently contribute their own 2x multiplicative factor through the existing per-extra hook loop (compounding to 4x total), two Spiral copies each independently add their own +1 replay, with zero per-enchantment-type math needed anywhere. `EnchantmentPool.BenefitsFromRepeatApplication` (renamed, and expanded) is the new, correctly-scoped gate for "is repeating this type actually worth offering."
- **Full enchantment pool enabled - the "subset" the user suspected was real**: `Swift`, `Sown`, `Adroit`, `Corrupted`, `Momentum`, and `Inky` had been withheld because their effect lives in `OnPlay`, which the native game only ever calls directly for a card's native slot-1 enchantment (inline inside `CardModel.OnPlayWrapper`'s per-replay loop), never through any hook extras could plug into - Phase 5 of the original plan assumed the only fix was a Harmony transpiler on that method, "the single highest-risk patch in this project." Re-decompiling `OnPlayWrapper` fresh (this game version) turned up a much lower-risk path: `Hook.AfterCardPlayed` - already a generic, per-listener hook - is called from *inside that same per-replay loop*, right after the native slot-1 `OnPlay` call for that iteration. `EnchantedRewardsModifier` now overrides `AfterCardPlayed` and manually invokes each extra's own `OnPlay` there, reaching the same "once per actual play/replay" granularity as the native path with no IL-level surgery at all - safe to call unconditionally for every extra, since `EnchantmentModel.OnPlay`'s base implementation is a no-op for every enchantment that doesn't override it. This is genuinely new, not-yet-live-tested code path (the `AfterCardPlayed` hook itself was already proven working via last round's Goopy fix, but invoking `OnPlay` through it is new) - please test these six specifically.
- With the pool now unified, `Corrupted`/`Momentum` join the Attack-only functional-restriction group (same reasoning as Sharp/Instinct/Vigorous); `Swift`/`Sown`/`Adroit`/`Inky` have no native `CanEnchantCardType` restriction in this game version, so there was nothing to relax for them (the user's assumption that Inky has a native Shiv-only restriction didn't hold in this build's decompile - nothing currently blocks it beyond the universal Status/Curse/Quest gate).

### Round 7 (duplicate flags, no save persistence, broken enchant-select preview)

- **Bugfix: stacking the same enchantment type showed two identical flags instead of one flag with a stack count**: `CardEnchantmentVisualsPatch` used to clone the native enchantment tab once per *instance* - correct when every extra is a different type, but a visibly broken duplicate when two instances share a type (expected since Round 6's stacking redesign: repeats are always independent instances, never merged). Fixed by grouping extras by type before drawing anything: a type with exactly one instance still shows its normal per-enchantment amount, same as before; a type with more than one instance shows a single flag labeled `xN` instead. Applies to the native slot-1 tab too, when one or more extras happen to share its exact type (it gets relabeled the same way; left completely alone otherwise).
- **Feature: extras now survive save/quit/reload** (previously a known, deliberately-deferred limitation - `ExtraEnchantments` is an in-memory-only `ConditionalWeakTable`, so every extra was silently gone on reload). BaseLib exposes exactly the right extension point for this: `ExtendedSaveHandlers<CardModel, SerializableCard>.RegisterSave` lets a mod attach extra save data to every card, keyed by a string id, wired transparently into both the plain single-player JSON save path and the binary packet path multiplayer sync uses - the same mechanism BaseLib itself uses internally to let `RelicModel`/`PotionModel`/`Player`/`Reward`/`RunState` do the same. New file `ExtraEnchantmentSave.cs`: the saved payload (`SerializableExtraEnchantments`) is just a list of the game's own `SerializableEnchantment` - the exact type the native slot-1 enchantment already serializes to/from, reused as-is. Restoring mirrors `EnchantmentService.Apply`'s fresh-application path exactly (`ApplyInternal` then `ModifyCard`, one independent instance per saved entry, never re-merged) - so N stacked copies of a type before a save/reload come back as N independent instances after, with the same per-instance-compounding math as a fresh application. Needed two extra one-time JSON-type registrations (`ExtendedSaveTypes.RegisterListSaveType`/`RegisterObjectSaveType`) for `List<SerializableEnchantment>` and the wrapper type itself, since - unlike `SerializableEnchantment` alone, already known to the native save system - neither had ever been used in a JSON-serialized context before. **Not yet live-tested** (needs an actual save/quit/reload cycle mid-run to confirm) - please verify specifically: stacked copies of the same type all come back independently, and multiple different types on one card all come back together.
- **Bugfix: the enchant-select screen's confirmation preview only showed the enchantment currently being applied, dropping everything the card already had**: root cause was entirely native, in `NEnchantPreview.Init` (confirmed by decompile), and had two parts. First, the "after" card is built via a run-scope clone (`RunState.CloneCard`) which - unlike the combat-scope cloning `CombatCloneSyncPatch` already handles - never sets the clone's `DeckVersion`, so `ExtraEnchantments.Get`'s existing `DeckVersion`-fallback lookup had nothing to fall back to and found none of the card's existing extras. Second, `Init` then calls `CardModel.EnchantInternal` for the enchantment being previewed, which unconditionally *replaces* the clone's native slot-1 enchantment - so even the card's existing *native* enchantment (not just extras) vanished from the "after" side, leaving only the one enchantment about to be applied, exactly matching the report. New file `EnchantPreviewPatch.cs` postfixes `NEnchantPreview.Init` to reattach whatever got discarded - the original card's existing native enchantment and its extras - onto the preview clone as our own extras, purely for display/preview-math purposes only (never re-running `ApplyInternal`/`ModifyCard` for them, since the clone already carries their cumulative effect from being deep-cloned off the original card, and their combat-math contribution is computed live off the instance regardless of which card it's nominally attached to). The "before" side of the preview was already correct (it shows the real, unmodified original card directly, not a clone) and needed no change.
- **Newly discovered, not yet fixed, narrow-scope issue found while investigating the above**: `Goopy.AfterCardPlayed` (native code) does `base.Card.DeckVersion.Enchantment.Amount++` unconditionally to sync its growing block bonus back to the persistent deck card - written assuming Goopy can only ever be the *native slot-1* enchantment. When Goopy is one of our extras instead, this line still fires (via the same generic hook dispatch that makes extras work at all) and increments whatever enchantment actually sits in the persistent card's native slot - which has nothing to do with Goopy at all if a *different* enchantment occupies slot 1. Net effect: playing a card with an extra Goopy on it silently corrupts an unrelated enchantment's `Amount` by +1 each time. Not fixed this round (out of scope for what was asked, and deserves care/testing on its own rather than a rushed patch); flagged here so it's not forgotten if an enchantment's Amount is ever seen drifting unexpectedly on a card that also has an extra Goopy.

### Round 8 (screenshots: inspect view drops a flag, loot options don't grey out, preview fix didn't take, native events still skip enchanted cards)

- **Round 7's enchant-preview fix rebuilt - it wasn't actually working**: the postfix on `NEnchantPreview.Init` fished the preview clone back out of the `%After` container's freshly-added child, but `RemoveExistingCards()` (called at the top of `Init`) only ever `QueueFree()`s the *previous* preview card, which Godot always defers to end-of-frame rather than removing immediately - so a stale, not-yet-freed child could still occupy index 0 when the postfix read it, silently fixing nothing. Rebuilt with no node-tree traversal at all: a prefix on `Init` captures the original card into a static field; a prefix on `CardModel.EnchantInternal` (the only *other* caller of it anywhere in the game besides native `FromSerializable`, which never hits this branch - confirmed by decompile) reattaches, directly onto the exact clone instance `EnchantInternal` is about to overwrite, both the native enchantment about to be wiped and the captured original's existing extras - before any of `Init`'s own subsequent card-node/visual code runs, so there's no timing race left to break.
- **Bugfix: a card's second enchantment flag disappearing when clicked to inspect (full-size popup view)**: same underlying cause as the preview bug, a different screen. `NInspectCardScreen.UpdateCardDisplay()` builds its displayed card via `CardModel.MutableClone()` - confirmed by decompile that *every* mutable clone's `AfterCloned()` step unconditionally resets `DeckVersion` to `null` (this is universal to cloning itself, not specific to any one call site - only combat cloning happens to set `DeckVersion` back afterward), so `ExtraEnchantments.Get`'s `DeckVersion`-fallback finds nothing here either. Unlike the preview case nothing here calls `EnchantInternal`, so the native slot-1 flag was never the problem - only extras vanished. New `InspectCardExtrasPatch.cs` postfixes `UpdateCardDisplay` to reattach the original's extras onto the clone and re-trigger just the enchantment-flag drawing (not a full visuals refresh, to avoid disturbing whichever upgrade-preview state the native code already chose).
- **Bugfix: the loot screen's two linked enchant options going quiet instead of greying out when one is picked**: a genuine native engine bug, confirmed by decompile - `NLinkedRewardSet.Reload()` wires each option's `NRewardButton.RewardClaimed` signal (one argument: the button itself) to `Callable.From(GetReward)`, where `NLinkedRewardSet.GetReward()` is a *zero*-argument private method. Godot's `Callable` trampoline rejects that mismatch the instant the signal is actually emitted ("Invalid argument count for invoking callable"), caught and only logged by the engine - meaning `GetReward()`'s real body (tell the rewards screen this option was claimed, mark the sibling skipped, remove the whole widget) never runs, while the enchant itself had already been applied moments earlier. Confirmed in the game's own log file at the exact moment of picking an option. This is a pre-existing bug in native `LinkedRewardSet` UI - it had zero other callers anywhere in the decompiled assembly before this mod started using it, so nothing had ever exposed it. Confirmed this round by decompiling the *entire* `sts2.dll` (`ilspycmd -p`, a full-project dump) and grepping every file for `EnchantmentStatus.Normal`: exactly two hits in the whole game, both inside `if (base.Status == EnchantmentStatus.Normal)` checks in `Sown.OnPlay` and `Swift.OnPlay` themselves - `Normal` is never *assigned* anywhere. Nothing in the clone chain touches it either (`EnchantmentModel.DeepCloneFields`, `CardModel.DeepCloneFields`, `CombatState.CloneCard`, `Player.PopulateCombatState` - none reset Status). So once one of these three fires, `Status` becomes `Disabled` for the rest of the run, not just the rest of that combat.

Why merging broke it: a second application merging its Amount into an *already-fired* (`Status == Disabled`) existing instance doesn't get a fresh chance to fire - it's permanently dead weight on an instance that will never trigger `OnPlay` again. Worse, `EnchantmentModel.DynamicExtraCardText` (the base property every enchantment's card text goes through) returns `null` whenever `Status == Disabled`, so the merged instance's text vanishes too - which is exactly what looked like Sown being "removed from the card entirely." Before Round 18, a repeat application always created a brand-new independent instance (fresh `Status.Normal`), so it kept working regardless of whether an earlier copy had already fired - independent stacking was actually the *correct* behavior for these three all along, not a limitation being worked around.

Fixed by removing Vigorous, Swift, and Sown from `EnchantmentService.MergeableTypes`, back to the same "independent instance, contributes its own share, `ExtraCardTextPatch`'s generic duplicate-line collapse covers the display" treatment as Instinct/Corrupted/Goopy. Sharp, Nimble, Adroit, Momentum, and Inky are unaffected - confirmed none of the five ever read or write `Status` at all, so there's no equivalent risk for them.

### Round 20 - Upgrade-preview screen dropped all extras; a legacy-merged Sown found in an existing save

Two more issues from continued live testing.

**Upgrade preview missing extras.** Reported: upgrading a multi-enchanted card in the "Choose a card to upgrade" preview (Rest Site, Armaments, etc.) showed the "after" (upgraded) card with only its native slot-1 enchantment - every extra's text and flag vanished. Root cause, confirmed by decompiling `NUpgradePreview` (the native screen behind this, distinct from `NEnchantPreview`): its `Reload()` builds the "after" card the exact same way `NEnchantPreview.Init()` does - `Card.CardScope.CloneCard(Card)` - but the reattachment logic EnchantPreviewPatch already installs for that clone was only ever wired to fire for `NEnchantPreview.Init`'s own capture, via `EnchantPreviewCloneCaptureShared.OriginalCardBeingPreviewed`. `NUpgradePreview.Reload` never set that, so its `CloneCard` call never got reattached at all.

Fixed by adding a capture prefix on `NUpgradePreview.Reload` (`UpgradePreviewExtrasPatch.cs`) that sets `OriginalCardBeingPreviewed` the same way, reusing the exact same `CloneCard` postfixes rather than duplicating the "which CloneCard ran" ambiguity a second time. One real difference from the enchant-preview case: `Reload` never calls `EnchantInternal` afterward (only `UpgradeInternal`), so there's no need to stash-and-swap the native slot's enchantment through extras the way `PutNewEnchantmentLast` does - the clone's native slot-1 enchantment is already correctly cloned by native `CardModel.DeepCloneFields`, and re-stashing it as an extra too would just duplicate it (a false "x2"). Added `EnchantPreviewCloneCaptureShared.NeedsNativeSlotSwap` (true only for the enchant-select case) so the shared reattachment helper knows which behavior to use for which caller.

**A legacy-merged Sown found in an existing save.** While confirming the above, a live diagnostic (temporarily logging each extra's Amount/Status/rendered text) turned up a Sown extra sitting at `Amount=2` on a save-file card - explaining an earlier, seemingly-mysterious "Sown shows no text" report from a few rounds back: that card's Sown had been merged to Amount=2 during the brief Round 18 window (before Round 19 reverted it) by something that never went through this mod's own reward-log line (most likely a native relic, since `NativeEnchantMultiSlotPatch`'s merge branch doesn't log the same way `EnchantReward.OnSelect` does), and if it had *also* already fired once in some earlier combat before Round 19's revert, Status would've stayed permanently Disabled from then on - the exact failure mode Round 19 diagnosed, just discovered here as already-baked-in save data rather than a live repeat application.

This isn't a live code bug (Round 19 already stops any *new* Sown/Swift application from merging) - it's stale data from before that fix, persisted forever because `SerializableEnchantment` only stores Id/Props/Amount, nothing about *how* an Amount was assembled. Since Sown and Swift both default to a plain Amount of 1 per application (neither has an entry in `EnchantmentPool.DefaultAmounts`), an Amount greater than 1 on either can only mean that many independent applications got wrongly merged - unambiguous, so it can be corrected automatically rather than needing manual save-editing.

Added `LegacyMergedStackFix.cs`: on every card restore, any Sown/Swift instance found with Amount > 1 is split back into that many independent Amount=1 instances - covering both restore paths, this mod's own extras (`ExtraEnchantmentSave.Set`) and the native slot-1 enchantment (a new postfix on native `CardModel.FromSerializable`, in case the merge happened to land there instead). Self-limiting: once corrected, every instance is back to Amount=1, so it's a no-op on every subsequent load - safe to leave in permanently. Vigorous shared the exact same Status bug and was pulled from `MergeableTypes` at the same time, but its default Amount is 8, not 1, so an observed Amount can't be unambiguously split back into "how many applications" without risking a wrong guess - deliberately left uncorrected pending an actual live report of a merged Vigorous.

Also removed the temporary diagnostic logging from `ExtraCardTextPatch` added earlier this round once it had done its job (confirmed live: Amount=2, Status=Normal, text rendering correctly for that Amount - the "missing text" was really the Round-19 bug, not a formatting bug).
